# 贡献：默认值与两种完全不同的"贡献"

> 起点是一个问题：规划里那句「普通用户无需为了使用好友、会话查看或其他基础功能而贡献存储或带宽」
> 是不是意味着默认不贡献？要不要默认打开、让所有节点都贡献？

---

## 1. 先纠正那句话的意思

那句话是 **§9.2「用户贡献设置」的最后一行**。它是一条**底线声明**：

> 贡献**不能成为**使用基础功能的前提。

它**不是**"默认不贡献"。而 §9.2 自己的清单恰好说明了它要的是什么：

- 「最大缓存空间，例如 **0**、500 MB、2 GB」—— 0 是合法档位
- 「**一键暂停**所有节点贡献」
- 「是否**仅在接入电源或非计费网络**时运行」

规划明确把贡献设计成**用户可控制、可随时暂停**的。这与"所有节点必须贡献"不相容。

---

## 2. 但不是所有"贡献"都一样 —— 这是关键区分

| | **会话内分发**（swarm） | **对陌生人的中继** |
|---|---|---|
| 你和这件事的关系 | 你**已经**在这场直播里、**已经收到**了数据 | 一个和你毫无关系的陌生人需要连到你 |
| 你的额外下载 | **零** | 零，但占上行 |
| 你的上行 | 本来闲置的那部分 | 额外的持续上行 |
| 解决什么问题 | **发布者上行瓶颈** | 跨 NAT 可达性 |
| 元数据暴露 | 同房间的人本来就互相可见 | 你要为一个陌生人做元数据观察者 |
| 能否默认开 | **可以** | 需要护栏 |

**所以默认值不一样：会话内分发默认开；对陌生人的中继默认 `auto`。**

---

## 3. 会话内分发：解决"所有人都从直播者拉"

### 3.1 为什么必须有

发布者的家宽上行通常只有几十 Mbps。几百个观众全从发布者拉，
**发布者必挂** —— 这不是优化问题，是直播能不能用的问题。

已经收到的观众帮同房间的人转发，是唯一的解法。

### 3.2 实测收益（确定性模拟，`test/live-swarm.test.js`）

| 场景 | 发布者推送次数 | 下降 |
|---|---|---|
| 20 人房间 · 不开启分发 | 25 | — |
| 20 人房间 · 全员可达 | **5** | **80.0%** |
| 30 人 · 可达 20% | 31（基准 38） | 18.4% |
| 30 人 · 可达 50% | 23（基准 38） | 39.5% |
| 30 人 · 可达 100% | 8（基准 38） | 78.9% |

### 3.3 ⚠️ 最值得注意的一行：**可达比例低≠分发没用**

现实里大部分观众在 NAT 后面，能被别人连到的只是一部分。
但"能被连到的少"不等于"分发白搭"：

> **可达比例只有 20% 时，发布者上行仍然下降 18.4%。**

因为每服务一个对端，发布者就少发一份。**分发不需要全员可达才有价值。**

### 3.4 策略上的三个细节（都容易做错）

**① 够用的人里挑持有最少的。**
持有最多的那个往往是刚加入、正在猛拉的节点；把大家都推给它，它就是下一个瓶颈。
挑"刚好够用"的，负载会自然摊开。

**② 房间太小时不启用。**
两三个观众时发布者直发更简单、延迟更低，加一层转发只是白增跳数。
分发是为"人多到发布者扛不住"准备的（默认阈值 4 人）。

**③ 拒绝必须给原因。**
`at-capacity` / `budget-exhausted` / `room-too-small` —— 对端据此换一个来源，而不是干等。

## 4. 对陌生人的中继：默认 `auto`，只在免费且安全时做

```yaml
contribution:
  mode: auto          # off | auto | on
  onlyOnPower: true       # 只在接电源时
  onlyOnUnmetered: true   # 只在非计费网络（移动网络/个人热点视为计费）
  monthlyUploadBudgetBytes: 21474836480   # 每月 20 GB 上限
  maxCacheBytes: 536870912                # 公开内容缓存 512 MB
```

`auto` 的判据（**全部满足**才贡献）：

1. **实测可达** —— `REACHABILITY.PROVEN`，即真的有人成功连入过。
   不是"我的 IP 看起来是公网"（见 `docs/reachability-detection.md`）。
2. **非计费网络** —— 不用别人的流量费来做好事。
3. **接电源** —— 不耗别人的电池。
4. **未超预算** —— 每月上行有硬上限。

### 4.1 为什么不能"所有节点都贡献"

三个理由，一个比一个硬：

**① 技术上经常做不到。** 本项目实测（`docs/reachability-detection.md`）：
NAT 后面且目的侧无端口映射时，**入站必然失败**。强制这类节点"贡献"，
等于让它们对外宣称一个不存在的能力 —— 别人的消息发进去石沉大海，
**比不贡献更糟**。

> 就用这台机器举例：它**没有公网 IPv4**（v4 是 `192.168.3.90`），只有公网 IPv6。
> 在纯 IPv4 网络里，没有任何对端能连进来。它当不了 IPv4 中继。

**② 代价落在用户身上。** 默认开中继 = 用陌生人的移动流量和电池做好事。
那不是"默认设置"，那是替别人花钱。

**③ 规划自己就反对。** §9.2 要求"一键暂停"、"仅在非计费网络时运行"、
缓存档位含 0 —— 这些开关的存在本身就说明贡献必须是可选的。

## 5. 完整默认值一览

| 项 | 默认 | 理由 |
|---|---|---|
| 会话内分发 | **开** | 零额外下载，直接决定发布者能不能扛住 |
| 分发房间下限 | 4 人 | 小房间加一层只是白增跳数 |
| 同时服务对端数 | 4 | 每个对端占一条连接与一份上行 |
| 分发上行预算 | 32 MB/分钟 | 贡献不该是无底洞 |
| 对陌生人中继 | **auto** | 只在实测可达 + 非计费 + 接电源 + 未超预算时 |
| 公开内容缓存 | 512 MB | 只缓存公开分享，私聊与未授权内容在上游被 `consent.js` 挡住 |
| 每月上行预算 | 20 GB | 硬上限 |
| 引导节点 | 仅实测可达者 | 绝大多数家用节点做不了 |
| 直播回放保存 | **关** | 占磁盘多，且牵涉别人的内容留存，适合显式选择 |

## 6. 测试覆盖（17 项）

| 组 | 项数 | 覆盖 |
|---|---|---|
| 来源选择 | 7 | 有对端就不回落发布者、**挑持有最少的**、没人才找发布者、房间太小不启用、不选自己、可用性只前进不后退、过期不算数 |
| 服务预算 | 5 | 正常接受并给上限、单次有上限、并发有上限且原因可解释、**每分钟预算用尽即停**、关闭时原因明确 |
| 收益实测 | 5 | 全员可达降 80%、**低可达比例仍有收益**、房间越大收益越明显、**同种子结果必须一致**、无样本时报 null 不编造 |

## 7. 还没做的

- **线上字节级搬运**：目前实现的是**策略层**（可用性、来源选择、服务预算）并已被完整测试；
  真正的分块传输仍走已有的 `LiveRoom` 补数据通道，**尚未按来源选择的结果去定向拉取**。
  换句话说：决策逻辑已经就位，接线还差一步。
- **打洞决定的扇出**：观众能不能互相连上取决于打洞/中继，
  这部分见 `docs/punch-and-incentives.md`。可达比例越高，分发收益越大（上表已量化）。
- **分布式存储的持久层**：公开内容缓存目前只有配置与上限，没有落地实现。
- **计费网络检测**：macOS 上需要读系统网络位置与接口类型，尚未实现（默认按"非计费"处理，
  这偏保守 —— 移动网络下会误判，见下）。

> 最后一条要如实说明：`onlyOnUnmetered` 目前**没有真正检测**计费网络，
> 所以 `auto` 模式在移动网络下**可能误判为可以贡献**。
> 在实现检测之前，建议移动网络用户把 `mode` 设为 `off`。
