# 中继与公网节点

规划 §9.1 把「中继节点」定义为"帮无法直连的设备转发加密通信"的节点。本文写清它怎么工作、
为什么必须存在、以及**它仍然能看到什么**。

---

## 1. 为什么必须有中继：这不是优化，是可达性问题

`docs/network-testing.md` 的虚拟网络环境给出了判决：

| 情形 | 直连 | 说明 |
|---|---|---|
| 同子网 / 公网主机 | ✅ 可行 | 基线 |
| 有一侧做了端口映射 | ✅ 可行 | 端口转发的效果 |
| 全锥形 NAT + 双方都先出站 | ✅ 打洞可行 | 需要信令交换公网端点 |
| **对称 NAT** | ❌ 打洞失败 | 同一 5 元组仍被拒 |
| **两侧都是 NAT、目的侧无映射** | ❌ 必然失败 | 最常见的情况 |

**对称 NAT 是移动网络的常态。** 只要用户里有一部分在这种网络后面，
没有中继就意味着**这部分人永远连不上**。

### 1.1 中继路线为什么一定能建立

```
   [NAT 后的 A] ──出站──► [公网中继 R] ◄──出站── [NAT 后的 B]
```

**NAT 永远允许出站。** 所以 A、B 各自主动连到 R，R 在中间转发 ——
这条路对 A、B 的 NAT 类型不敏感，对称 NAT 照样能用。
唯一要求是 **R 自己必须公网可达**。

## 2. 实现

| 文件 | 作用 |
|---|---|
| `src/host/crypto.js` | X25519 + HKDF + AES-GCM 端到端加密 |
| `src/host/relay.js` | `RelayServer` / `RelayClient` / `RelayTransport` / 转发闸门 |
| `src/host/identity.js` | 身份文档（自签名，用于交换加密公钥） |
| `src/host/net/lan.js` | 握手公告里带上 `encryptionKeyId` 与中继能力 |

### 2.1 直连优先，连不上再走中继

`RelayTransport` 对上层只是一个普通的 `NodeTransport`：

```js
send(peerKey, envelope) {
  if (直连可达) return inner.send(...);   // 直连不经过任何第三方，也不花别人的带宽
  return relayClient.forward(...);        // 只有直连确实不可达时才动用中继
}
```

上层（peers / live / share / index.js）**不需要知道**某条消息是直连送出去的还是中继转的。
但每条记录都带 `relayed` 标记 —— 用户有权知道某条消息经过了第三方。

### 2.2 加密是必要条件，不是可选项

中继对**明文私聊直接拒绝转发**（`classifyForward`）。所以不加密的话，
经过中继的消息根本发不出去 —— 加密不是"顺便加的安全功能"，而是这条链路的**准入条件**。

```
签名（Ed25519）→ 证明"这条是谁发的"，全体可见、可被中继校验（用于反垃圾）
加密（X25519）→ 保证"只有收件人能读"，中继无法解开
```

两者互相独立：**加密不等于真实，签名也不等于保密。**

### 2.3 加密公钥怎么拿到（不让中继变成中间人）

这是最容易做错的地方。如果由中继告诉你"B 的加密公钥是 X"，
**中继就可以把 X 换成自己的公钥，从而解密你和 B 的全部通信。**

所以身份文档是**自签名**的：

```js
document = { publicKeyId, encryptionKeyId, nickname, updatedAt, sig }   // sig 由 Ed25519 私钥签
```

中继只能**转交**，不能**伪造** —— 它没有 B 的签名私钥。
它仍然可以"不给"或"给旧的"，所以文档里带 `updatedAt`，
接收方保留最新版本，并在**加密公钥发生变化时单独提示用户**（可能是换设备，也可能是攻击）。

## 3. 中继看不到什么（硬约束，不是承诺）

中继对每个要转发的信封做一次分类判断，**fail-closed**：

```
载荷是密文（X25519+AES-GCM）           → 转发（中继没有接收方私钥，解不开）
载荷是明确公开的类型                    → 转发
   在线状态 / 公开直播事件 / 公开分享公告（scope 必须是 public）/ 插件清单与评分
其它一切                                → 拒绝转发并计数
```

**白名单而不是黑名单。** 上游将来新增一种事件类型时：
黑名单会**静默放行**新东西；白名单只会"少转发"。
少转发的表现是功能缺失，不是隐私泄露 —— 这个取舍是刻意的。

实测（`test/network/relay.test.js`）：

```
明文私聊被中继拒绝（fail-closed），原因回传给发送方：refused:plaintext-refused
中继转发 1 条密文（289 字节）并完成拆包；登记 2 个对端，转发 1006 字节
```

## 4. 中继仍然能看到什么（必须如实说）

**没有被消除、也不应该假装被消除的东西：**

| 中继能看到 | 说明 |
|---|---|
| **通信关系** | 谁在和谁通信（公钥标识） |
| **消息大小与时间** | 信封长度、频率、时间分布 |
| **在线状态** | 谁什么时候在线、挂了多久 |
| 它可以**拒绝服务** | 规划 §12.5 已把它列为已知威胁 |

**能看到的正文：零。** 这是协议层保证的（中继没有收件人私钥），不是策略承诺。

缓解方向（尚未实现）：用户选择自己信任的中继、同时使用多台中继、填充固定长度掩盖消息大小。

## 5. 公网节点怎么知道自己"真的能被连上"

这是一个容易被自我欺骗的地方：**在配置里写 `serve: true`，在 NAT 后面是没有任何用的** ——
别人根本连不进来，而你还在向别人宣称自己是中继。

所以本实现区分三种状态，并且只用**实测证据**：

| 状态 | 判据 | 界面文案 |
|---|---|---|
| `client-only` | 只使用别人的中继 | 仅使用别人的中继 |
| `unproven` | 配置了 `relay.serve`，但**从未有节点成功连入过** | 已配置中继但未被验证 |
| `reachable` | **实测有节点主动连入过** | 公网可达 · 可当中继 |

判据是 `reachability.inboundPeers > 0` —— 只统计**方向为 inbound 的握手**。
"我在配置里开了" 和 "真的有人连得进来" 是两件事，界面上分开显示。

对外宣称中继能力时，`relay.verified` 字段如实反映这一点，避免误导别人把消息
发给一个根本连不上的地址。

## 6. 配置

```yaml
- insert:
    - id: dsh-chat
      name: dsh-chat
      config:
        relay:
          enabled: true                # 是否使用别人的中继
          serve: false                 # 本机是否对外提供中继（只有公网可达才应打开）
          servers:                     # 已知的公网中继
            - 203.0.113.7:47800
          useDiscoveredRelays: true    # 是否采用信标/握手里自称可中继的节点
          policy:                      # 服务端策略（规划 §9.2 要求用户可设）
            maxPeers: 32
            maxEnvelopeBytes: 262144
            maxForwardBytesPerMinute: 8388608
            peerTtlMs: 90000
            requireSealedForPrivate: true
```

界面：**节点 → 中继（公网节点）**。可以看角色、可达性证据、已接入的中继与负载、
经中继可达的节点、以及中继流量统计；并支持手动填入一台中继地址。

> 跨网段时**广播发现到不了别的网络**，手动地址、邀请码、引导节点是唯一入口。

## 7. 测试覆盖（21 项）

| 组 | 项数 | 覆盖 |
|---|---|---|
| 密码学与身份文档 | 4 | 只有收件人解得开、第三方与篡改失败、前向保密、文档自签名、中继伪造被拒、旧身份迁移 |
| 转发闸门 | 4 | 密文放行、**明文私聊拒绝**、公开类型白名单、公开分享 scope 校验、未知类型拒绝 |
| 登记表 | 5 | 容量上限、重连不重复占位、超时清理、断连清理、伪造文档不入库 |
| 服务器转发（真实产品路径） | 6 | 密文互通且中继看不到明文、拒绝明文并回原因、目标未挂号回 unreachable、文档原样转交、容量拒绝 |
| 端到端 | 2 | **对称 NAT 下直连必失败 → 加中继就通**（双向加密消息） |

端到端那条的实测输出：

```
对称 NAT + 无映射 → 直连被拒（这就是需要中继的全部理由）
对称 NAT 两侧：直连被拒 → 各自**只做出站**挂号到公网中继 → 双向加密消息跑通
中继统计：转发 2 条、拒绝明文 0 条、登记 2 个对端、转发字节 2024
```

## 8. 尚未实现

- **打洞**：虚拟环境已证明全锥形 NAT 下可行，但产品里还没做（需要信令交换公网端点）。
  目前是"直连 → 不行就中继"，跳过打洞这一步。打洞能省掉中继带宽，值得做。
- **多中继与故障转移**：`forward()` 会依次尝试所有已登记的中继，
  但没有"哪个中继更优"的选择策略，也没有负载感知。
- **中继激励与信誉**：规划 §9.5 讨论过，本版本没做（也不建议在 MVP 引入代币）。
- **固定长度填充**：中继仍能从消息大小推断内容特征。
- **中继服务的运行时开关**：`relay.serve` 属于启动期配置，改它需要重启 DSH。
