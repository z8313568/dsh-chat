# 网络测试环境与结果

针对"不同网络下的连接与数据"这一目标建立的测试环境，以及实测结果。

**一句话结论**：把网络拆成**链路质量**、**链路走在哪里**、**谁能连谁**三个维度分别造环境。
前两个维度用故障注入代理与真实网卡测（21 项）；第三个维度——NAT、防火墙、真实丢包——
用一套**用户态虚拟互联网**测（22 项）。**43 项网络用例全部通过。**

剩下的不可测部分是**物理链路与真实运营商路径**（不是机制问题，是参数问题），
在 §8 逐条列出。

---

## 1. 测试环境由三部分组成

| 层 | 文件 | 作用 | 用例数 |
|---|---|---|---|
| **故障注入** | `test/network/fault-proxy.js` | 夹在两个节点之间的 TCP 代理，注入延迟/抖动/黑洞/RST/半关闭/带宽限制/分片/损坏 | 13 |
| **拓扑变化** | `test/network/topology.test.js` | 换**地址**而不是换质量：回环 IPv4、回环 IPv6、真实网卡、跨地址族、信标发现 | 8 |
| **虚拟互联网** | `test/network/virtual-internet.js` + `virtual-link.js` | 用户态搭出多子网 + NAT + 防火墙 + **真实丢包链路**，测"谁能连谁" | 22 |
| **真实设备实验台** | `scripts/net-lab.mjs` | 可执行的命令行工具，在两台真机上跑同一套测量 | — |

所有用例都跑**真实的** `LanTransport`：真实 TCP、真实 WebSocket、真实 Ed25519 握手、
真实信封签名。没有一处 mock 网络。

### 1.1 为什么环境要单独做成"可注入"的一层

直接用真机测有几个绕不过去的问题：环境不可复现、失败无法二分、极端条件（比如黑洞、
RST、逐字节分片）在正常网络里根本不会出现。

但注入器本身如果不严谨，会比不测更糟 —— 它会造出**现实中不存在的网络**，
然后让你去修一个本来没问题的东西。这一点踩了三次，都记在 §4。

## 2. 链路质量矩阵（13 项，全部通过）

| # | 场景 | 注入 | 结果 | 实测 |
|---|---|---|---|---|
| ① | 理想链路 | 无 | ✅ | 8 条消息往返 **17ms**，载荷哈希一致 |
| ② | 高延迟 | 单向 150ms | ✅ | 4 条消息完成，数据一致 |
| ③ | 高抖动 | 20~500ms | ✅ | 4 条消息完成，数据一致 |
| ④ | 逐字节分片 | 每 1 字节一次转发 | ✅ | 745 个上行分片，120 字节 ×3 完整 |
| ⑤ | 带宽限制 | 32 KB/s | ✅ | 16 KB 载荷 **513ms** 送达，数据一致 |
| ⑥ | 黑洞 | 连接后冻结 1.5s | ✅ | 恢复后 3 条消息完整，**零丢失零损坏** |
| ⑦ | 连接重置 | RST | ✅ | 对端判定离线；换干净链路**重连成功** |
| ⑧ | 半关闭 | 只发 FIN | ✅ | 对端正确判定离线（回归曾经的"永远在线"bug） |
| ⑨ | 握手超时 | 冻结 > 握手上限 | ✅ | 干净断开、计数正确、**之后仍能正常连接** |
| ⑩ | 字节损坏 | 100% 翻转 bit | ✅ | 握手被拒绝、**零有效消息投递**、节点不崩 |
| ⑪ | 恶劣组合 | 80ms+120ms抖动+7B分片+256KB/s | ✅ | 4 条 200 字节消息完整 |
| ⑫ | 多节点并发 | 8 节点各自不同链路 | ✅ | 8/8 握手成功，消息来自 8 个不同身份 |
| ⑬ | 反复断连重连 | 8 轮 | ✅ | B 累计握手 8 次，**当前连接数 0，无残留** |

**每一条都同时断言两件事**：连接行为（该通的通、该断的断得干净）与**数据完整性**
（收到的载荷与发出的逐字节一致，且无重复）。后者是重点 —— "连上了"不等于"数据对了"。

## 4. 这套环境抓到的问题

### 4.1 注入器自己的三个缺陷（如果不修，测试结论全是假的）

| # | 缺陷 | 表现 | 根因与修法 |
|---|---|---|---|
| H1 | **造出乱序** | `{jitterMs, chunkSize}` 组合必然失败，单独用任一参数都正常 | 每个分片独立抽延迟 → 分片 1 延迟 100ms、分片 2 只延迟 5ms → **乱序**。TCP 不会乱序。修法：维护"下一批允许发送的时刻"，单调排队 |
| H2 | **两段调度互相插队** | `chunkSize + bandwidthBps` 组合必失败 | 先按延迟排一次、回调里再按带宽排一次 → 两个定时器拿到同一到期时刻，Node 按插入顺序触发 → **后一个分片先写出去**。修法：延迟一次算完，只调度一次 |
| H3 | **延迟按分片放大** | 握手从应有的 ~160ms 变成 ~800ms，机器一忙就抖到超时 | 450 字节的信封切成 65 个分片、各自独立延迟 ≡ MTU 只有 7 字节的网络。修法：**延迟按一次 write 算一次**，分片只在这次 write 内部按 `setImmediate` 拉开（用来逼出对端的帧重组路径） |
| H4 | 定时器里 `emit('error')` 二次抛出 | 偶发卡死 | `EventEmitter` 在没有 `'error'` 监听器时会让 `emit('error')` 本身抛错，等于把异常从定时器再扔一次。修法：只记账，有监听器才上抛 |
| H5 | 所有用例共用一个清理账本 | 越靠后的用例越慢，最后那个极端场景直接超时 | 十几个代理的定时器一起跑，事件循环被压满。修法：**每条用例自己收尾** |

**这五条的共同教训**：H1–H3 都表现为"被测代码在恶劣网络下不行"，
如果没有逐层二分（先换纯 TCP 服务端、再单独扫每个参数、最后才怀疑被测代码），
就会去改三个本来正确的模块。H4、H5 则说明**测试环境的资源管理本身就是被测对象的一部分**。

### 4.2 被测代码的真实缺陷（拓扑层抓到的）

| # | 缺陷 | 影响 | 修法 |
|---|---|---|---|
| P1 | **`URL.hostname` 对 IPv6 保留方括号** | `new URL('ws://[::1]:1/').hostname === '[::1]'`，直接交给 `net.connect` 失败 → **IPv6 完全连不上** | 新增 `unbracketHost()`，拨号前去掉方括号 |
| P2 | **地址正则用"第一个冒号"切分** | `^[^\s:]+:\d{1,5}$` 对 `[::1]:1234` 必然失败 → IPv6 地址进不了配置、邀请码解不开 | 新增统一的 `parsePeerAddress()`，支持 `[v6]:port`；无方括号的 IPv6 明确拒绝而不是猜 |
| P3 | **通配监听地址被当成可拨号地址通告** | `listen.host = 0.0.0.0` 时，信标和邀请码里写着 `0.0.0.0:47800` —— 看着正常，**拨过去必然失败** | 监听地址与通告地址分离：通配时换成一个具体的非内部地址 |

P3 是在**实际运行 net-lab 工具时**发现的（输出里赫然写着 `dial 0.0.0.0:47850`），
不是测试抓到的 —— 说明"能跑起来的工具"本身也是一种验证手段。

## 5. 真实设备实验台（net-lab）

```sh
# 设备一：监听 + 回显
npm run lab -- serve --host 0.0.0.0 --port 47800 --name 客厅台式机

# 设备二：拨号 + 压测
npm run lab -- dial 192.168.3.90:47800 --count 200 --size 512
```

重复/乱序/损坏计数、以及**内容完整性校验**（服务端回显摘要与本地发出的逐条比对）。

## 6. 虚拟互联网：把"谁能连谁"也变成可测的

故障注入代理改的是**链路质量**，拓扑测试改的是**地址**——两者都改不了"**谁能连谁**"。
而后者才是 P2P 应用真正的生死线：NAT 后面能不能被连上、防火墙放不放行、打洞可不可行。

本机 `sudo` 不可用（`dnctl`/`pfctl` 要 root），Docker 守护进程没起（colima 需要拉 ~1GB 镜像）。
所以这一层用**用户态代码**搭出来：子网、网关、NAT 表、防火墙规则、端口映射，全部真实生效。

### 6.1 拓扑模型

```
   lan-a (10.0.1.0/24)                     lan-b (10.0.2.0/24)
     [主机 A 10.0.1.5]                        [主机 B 10.0.2.5]
          │                                        │
     [gwA 10.0.1.1 / 公网 203.0.113.1]      [gwB 10.0.2.1 / 公网 203.0.113.2]
          │                                        │
          └──────────────── wan ───────────────────┘
```

判决规则与真实 NAT 一致：**出站永远放行并建立映射；入站默认拒绝**，
除非有静态端口映射，或存在一条"目的地址正好等于来包源地址"的动态映射。
最后半句就是**打洞**的全部原理。

### 6.2 NAT 语义实测（8 项）

| 场景 | 结果 | 说明 |
|---|---|---|
| 同子网直连 | ✅ | 基线 |
| 跨 NAT 无端口映射 | ❌ 被拒 | `nat-inbound-blocked` —— **这就是当前产品在真实网络里的处境** |
| 目的侧有端口映射 | ✅ | 端口转发的效果 |
| 只有一侧有映射 | ❌ 被拒 | 必须**目的侧**有映射，自己有没有不算 |
| **打洞（全锥形 NAT）** | ✅ | A 先出站后，来自**同一对端**的回包被放行 |
| 打洞对陌生地址 | ❌ 被拒 | 映射是"针对某个对端"的，不是对所有人敞开 |
| 打洞（对称 NAT） | ❌ 失败 | 同一 5 元组仍被拒 —— **移动网络的典型情况，必须靠中继** |
| 全锥形复用映射 | ✅ | 同一目标公网端口稳定，对方算得出来 |
| 公网主机（无 NAT） | ✅ | 直接可连 |

### 6.3 防火墙（3 项）

按端口拦截、放行其它端口、以及**拒绝原因可区分**（`firewall-blocked-port` vs `no-mapping`）——
后者很重要：排查时"被防火墙拦了"和"根本没有映射"要做的事完全不同。

### 6.4 真实丢包（7 项）

这是本环境最值得说的一块。**TCP 代理原理上无法模拟丢包**：在字节流里丢几个字节是"数据损坏"，
两端的 TCP 栈根本不知道少了东西。

所以这里自己实现了一条**跑在 UDP 之上的可靠字节流**（`virtual-link.js`，相当于一个迷你 TCP）：
应用字节 → 切段编号 → 经 UDP 发出（**这一段会真的丢/延迟/乱序/重复**）→ 接收方按序重组 →
缺失的段由发送方超时重传。于是"丢包"变成了应用能真实感受到的**停顿 + 恢复**。

| 场景 | 实测 |
|---|---|
| 无损基线 | 4KB 用 **16ms** |
| **丢包 20%** | 真实丢弃 2 段，**重传 11 次**，364ms，内容逐字节一致 |
| **丢包 50%** | 耗时 **9845ms**（无损 20ms），重传 195 次，内容一致 |
| **丢包 100%** | 2500ms 内**零交付**，不假装成功 |
| 黑洞 1.2s | 丢弃 80 段，重传 80 次，**1293ms 内完整补齐** |
| 乱序 40% + 重复 30% | 重组 6 段，内容逐字节一致 |
| 30ms + 60ms 抖动 | 4KB 用 103ms，内容一致 |

"丢包 50% 从 20ms 变成 9845ms" 这个数字本身就是结论：**丢包不是"少一点数据"，而是数量级的延迟放大。**

丢包用**确定性伪随机**（固定种子），所以同样的参数每次跑出同样的结果 ——
网络测试如果每次随机，就没法判断"失败是链路造成的还是运气不好"。

### 6.5 跨 NAT 的端到端数据通路（3 项）

不只是判决，还有真实字节流：端口映射之后，`[调用方] → 虚拟链路 → [NAT 内的真实 TCP 服务]`
可以跑通，44 字节原样往返；在**丢包 25%** 的跨 NAT 链路上，3000 字节仍然完整往返。

### 6.6 广播域隔离（1 项）

同子网才是同一个广播域；跨子网的广播不会被网关转发。
这条**直接解释了**为什么"局域网发现"跨不了网络，以及为什么必须有
手工地址 / 邀请码 / 引导节点。

## 7. 仍然测不了的部分（物理链路与真实运营商路径）

虚拟环境能把**机制**测清楚，但测不出**真实世界的参数**。这一节比"通过"更重要。

| 场景 | 虚拟环境能做什么 | 仍然测不了什么 |
|---|---|---|
| **NAT 穿透** | ✅ 已测：无映射被拒 / 端口映射可行 / 全锥形可打洞 / 对称 NAT 不可行 | 真实运营商是哪种 NAT、映射存活多久、端口分配是否可预测 |
| **跨运营商 / 跨地域时延** | ✅ 可注入任意延迟与抖动 | **真实路径的时延到底是多少**（注入的是假设，不是测量） |
| **移动网络抖动** | ✅ 可注入高抖动 + 高丢包 | 真实蜂窝链路的动态特性（切换基站、隧道、信号衰落） |
| **企业防火墙 / DPI** | ✅ 可按端口/方向拦截 | 真实设备是否识别并阻断 WebSocket、是否有 TLS 中间人 |
| **纯 IPv4 ↔ 纯 IPv6** | ✅ 可构造只有单一地址族的主机 | 真实双栈环境下的 Happy Eyeballs 行为、DNS64/NAT64 |
| **广播被路由器阻断** | ✅ 已测（跨子网广播不可达） | 真实家用/企业 AP 的客户端隔离、多播抑制策略 |
| **真实丢包链路** | ✅ 已测（20%/50%/100%，含重传代价） | 真实链路的丢包**模式**（突发丢包 vs 随机丢包） |
| **多节点大规模组网** | ✅ 测到 8 并发（受本机端口/CPU 限制） | 几十上百节点的收敛、引导节点压力、NAT 映射表容量 |

**一句话**：虚拟环境回答"**这个机制行不行**"，真实设备回答"**在这条具体链路上行不行**"。
两者都需要，不能互相替代。

### 7.1 已知的实现层限制（不是测试问题，是产品还没做）

- **没有 NAT 打洞、没有中继**。虚拟环境已经证明：无映射时直连必然失败，
  全锥形 NAT 下打洞**可行**，对称 NAT 下**必须靠中继**。这三条结论直接指出了下一步该做什么。
- **UDP 信标只在同一广播域内有效**，且当前只用 `udp4`。
- **邀请码里的地址是本机探测到的第一个非内部地址**，多网卡机器上不一定是对方能到达的那个。

### 7.2 建议的下一步实测（按优先级）

1. **两台设备同一 Wi-Fi**：`serve` + `dial`，确认局域网发现与直连。（最容易，先做这个）
2. **一台设备走手机热点**：验证跨网段失败的具体形态（虚拟环境已预测会被 NAT 拒绝）。
3. **一端做端口映射**：验证"有公网可达方"时跨网络连通（虚拟环境已证明可行）。
4. **判定真实 NAT 类型**：用两个 STUN 类服务看映射是否复用 —— 这决定打洞值不值得做。
5. **长时间稳定性**：`serve` 挂 24 小时反复 `dial`，看是否有连接泄漏（本机 8 轮重连无残留）。

### 6.1 建议的下一步实测（按优先级）

1. **两台设备同一 Wi-Fi**：`serve` + `dial`，确认局域网发现与直连。（最容易做，先做这个）
2. **一台设备走手机热点**：验证跨网段是否失败、失败得多干净。
3. **一端做端口映射**：验证"有公网可达方"时的跨网络连通性。
4. **长时间稳定性**：`serve` 挂 24 小时，期间反复 `dial`，看是否有连接泄漏（本机 8 轮重连无残留）。

## 7. 怎么跑

```sh
npm run test:network    # 43 项网络用例（链路质量 13 + 拓扑 8 + 虚拟网络 22）
npm run test:virtual    # 只跑虚拟互联网那 22 项（NAT / 防火墙 / 真实丢包）
npm run test:unit       # 162 项其余用例
npm test                # 全部 205 项，约 15 秒
npm run lab -- --help   # 真实设备实验台
```

> 网络用例会**真实占用端口、真实广播 UDP 信标**。拓扑用例的信标跑在 `47911`
> 与 `47912` 上，与插件默认的 `47899` 错开，避免干扰你正在运行的 DSH 实例。
