## 二、真实环境验证（最重要的一项）

### 2.1 方法

`scripts/verify-live-node.mjs` 以一个**完全独立的 Node 进程**扮演"另一个用户节点"：
它不读插件的任何内部状态，只使用与插件同源的传输实现，通过 UDP 信标与运行中的
DSH 里的 dsh-chat 节点交互。

这验证的正是规划「阶段 0」的验收标准 ——
**「两个独立用户实例能够安全交换测试消息」** —— 而且是在真实环境里，不是在测试环境里。

### 2.2 实测输出

```
=== dsh-chat 真实节点连通性验证 ===
[+    4ms] 外部节点指纹 a3410f90-95753c5d-447b10cd-ef0ad741，监听 127.0.0.1:63511
[+    4ms] 等待端口 47899 上的信标，或等待运行中的插件主动连过来…
[+    9ms] 握手完成（inbound）→ 未命名节点 · 指纹 2fe33ea8-d8c4380f-9434d9ae-63472359
  ✔ 与运行中的 dsh-chat 节点完成双向身份握手
  ✔ 对端提供了指纹 — 2fe33ea8-d8c4380f-9434d9ae-63472359
  ✔ 对端身份标识是自描述的 Ed25519 公钥 — ed25519:gwLVYV65Wihoq1…
  ✔ 已向对端发出带签名的信封
  ✔ 收到对端发来的信封 — kind=presence
  ✔ 收到信封的签名可独立验证
  ✔ 本地 codec 没有拒绝任何收到的东西 — {}

=== 结果：通过 ===
握手方向：inbound；对端指纹：2fe33ea8-d8c4380f-9434d9ae-63472359
```

### 2.3 这份输出证明了什么

1. **指纹对齐**：`2fe33ea8-d8c4380f-9434d9ae-63472359` 与
   `~/.dsh/dsh-chat/identity.json` 里插件自己生成的身份**完全一致** ——
   证明对端确实是那个正在运行的插件，不是一个恰好也叫这个名字的东西。
2. **inbound 方向**：是**插件主动发现并连过来**的（它拿到了我们发的 UDP 信标，
   自动回连）。也就是说插件的"发现 → 连接 → 握手"整条链路是自己在跑的，不是被脚本推着走的。
3. **9 毫秒**：握手用时 9ms，没有人为延迟。
4. **双向**：我们发出的信封被接受，对端也回发了 `presence`，且签名能独立验证。

### 2.4 一个已知的平台限制（如实记录）

握手方向是 inbound 而不是 outbound，原因是 macOS 上多个 socket 用 `SO_REUSEADDR`
绑同一个 UDP 端口时，收到的包只会投递给其中一个。插件自己也绑着 47899，
所以脚本收不到插件发的信标 —— 但插件收得到脚本发的。

这不影响结论（握手与签名校验的强度与方向无关），但值得记下来：**在同一台机器上跑两个
以上节点时，信标投递是有竞争的**。跨机器时不涉及这个问题。

### 4.1 测试过程中抓到的真实 bug

这些不是写测试时的误报，而是测试真的拦下了缺陷。列出来是因为它们说明了测试的价值：

| # | 缺陷 | 表现 | 根因 |
|---|---|---|---|
| 1 | **服务端不回 Close 帧** | 标准客户端 `close()` 之后永远挂住 | 违反 RFC6455 §5.5.1。只有拿 **Node 内置 WebSocket 客户端**对打才暴露；自己连自己不会发现 |
| 2 | **`end` 事件未处理导致"永远在线"** | 一方断开后另一方一直显示在线，重连逻辑形同虚设 | HTTP `upgrade` 出来的 socket 是**半开**语义：对端发 FIN 只会触发 `end`，不触发 `close`。单看握手和消息往返完全发现不了 |
| 3 | **分享对象 id 自指** | `create()` 出来的分享立刻通不过 `verify()` | `id = hash(内容)` 却把 `id` 自己算进了内容 |
| 4 | **清单/评价同样的自指问题** | 发布的清单/评价自校验失败 | 同上；另外签名覆盖的字段集与校验用的字段集不一致 |
| 5 | **作者回复破坏签名** | 回复一条评价后，`importRating` 再也通不过 | 把可变注解写进了被签名的对象。修法是让回复成为独立签名记录 |
| 6 | **`ratingsFor` 包装即破坏** | 返回值通不过自己的校验 | `{...rating, verified}` 多出来的字段参与了内容哈希 |
| 7 | **直播事件重复投递** | 每个订阅者收到两遍 | 引擎与房间各投递一次 |
| 8 | **补拉上限与环形容量混用** | 调小"单次补拉上限"会意外截短回放 | 两个语义不同的配置用了同一个键 |

第 1、2 两条是**只有做真实端到端测试才会暴露**的缺陷 —— 它们的共同特征是：
单看协议的每一步都"对"，但两端合起来就不对。这也是为什么验证报告第一节的
"外部进程握手"值得单独做一次。

### 4.2 一次验证方法论上的失败（必须记下来）

交付之后，用户在界面上拿到的是 **「未知方法: dsh-chat/rpc」**。

根因：`connection.rpc.call(channel, endpoint, payload)` 发出的信封里，
**`method` 字段承载的是端点名**（`'dsh-chat/rpc'`），业务方法名在 `payload.method` 里。
第一版把 `message.method` 当成了业务方法名。修法是读 `message.payload.method`。

契约其实一直在手边 —— `@deepseek-ai/dsh-client-connection/lib/client.js`：

```js
const message = { type: 'client-request', rpcId, method: endpoint, payload };
```

**但真正的问题不是这个笔误，而是我当时的验证只做到这两条：**

| 我验证过的 | 它能证明什么 | 它不能证明什么 |
|---|---|---|
| 路由挂载成功（README §3.6 的 401） | 路由存在、认证已继承 | 请求能不能被**解析** |
| 无认证返回 401 | 安全边界正确 | 有认证时能不能**跑通** |
| slot 注册为 `active: true` | 模块被 apply 了 | 组件里的 RPC 调用能成功 |

也就是说：**"接口在那儿"和"接口能用"是两件事，我把前者当成了后者。**
当时我在报告里写"RPC 无认证返回 401 ✅"，读起来像个通过项，
但它其实完全没有覆盖用户实际会走的那条路径。这是比那个笔误更值得记下来的教训。

补上的东西：

1. `test/rpc.test.js` —— 按**真实报文形状**构造请求，覆盖解析、端点校验、畸形输入、
   异常转换、降级通道、SSE 门禁（21 项）。
2. 同一文件里的**结构性交叉检查**：静态提取 Host 的 `rpc.register('…')` 与
   Client 的 `client.call('…')`，断言前者覆盖后者。方法名是字符串、没有类型检查，
   这一个测试就能挡住"改名忘改另一边"和"新加调用忘了加处理器"两类问题。
3. 报告口径改了：只有**跑通往返**才算验证过 RPC；"路由存在"单独列，不算通过项。

### 4.3 第二次方法论失败：把一个静默空操作当成"做完了"

RPC 修好之后，用户又反馈：**「开启直播与分享会话的按钮都无法点击」**。

按钮本身完全正常。真正发生的是：点击 → `ctx.layout.selectPanel('dsh-chat')` 切主面板
→ 主面板再打开对话框。而 `layout` 是这么取的：

```js
const layout = ctx.get?.('layout');   // ← apply 那一刻的一次性快照
const openPanel = () => { try { layout?.selectPanel?.(PANEL_ID); } catch {} };
```

服务当时没就绪 → `layout` 永远是 `undefined` → `?.` 让整行静默通过 → **什么都没发生**。
用户看到"点了没反应"，描述成"按钮坏了"，但按钮一直是好的。

两个问题，第二个更严重：

1. **取值方式错了。** 正确写法是 `ctx.inject(['layout'], (c) => { … c.layout … })`，
   它会在服务出现时重新执行回调。参考实现（`@xmanrui/dsh-im` 的
   `plugin-src/client/plugin-page.js`）就是这么写的，我当时看到了却没照做。
2. **失败是静默的。** 整条路径上没有任何一处会告诉用户"切换面板这一步没成功"。
   一个 `?.` 加一个空 `catch`，故障就消失了——它不是被处理了，是被藏起来了。

修法分两层，第二层才是关键：

- 表层：用 `ctx.inject` 正确获取服务，`openPanel()` 返回布尔值表示是否真的切了。
- **结构层：把因果反过来。** 对话框不再依赖"切面板成功"，而是**由会话页入口自己原地弹出**。
  能不能切到主面板只是顺便的事，切不动也不影响主操作。
  一句话原则：**一个 UI 动作的结果，不应该依赖另一个无关部件的可用性。**

补的测试（`test/client-render.test.js` 里的「会话页入口：点击必须立刻有结果」）：

- 完全不提供 `onOpenPanel`（模拟 layout 永远不可用）时，点「分享会话」**必须**弹出对话框；
- `onOpenPanel()` 返回 `false` 时，对话框照常打开，并明确告诉用户"主面板未自动打开，操作不受影响"；
- 切面板成功时**不**显示那句多余的说明；
- 从「开启直播」一路走到进入直播间，全程不依赖主面板。

### 4.4 第三次方法论失败：改了症状，没改结构

RPC 与"点了没反应"都修完之后，用户反馈：**「点击开启直播直接跳转到了面板，但是没有开始直播」**，
并追问了一句很关键的话：「后台进行直播了吗？」

先说结论：**没有，一个字节都没出去。** 这一点可以从数据直接证明（见 §4.5）。

但代码上我确实又错了一次，而且这次错得更值得说 —— 因为**它是被上一条修复"制造"出来的**：

| 上一轮 | 这一轮 |
|---|---|
| 问题：按钮点了没反应，因为 `layout` 拿不到，切不了面板 | 我把"切面板"修好了 |
| 我顺手让按钮**自己渲染对话框**，并"顺便"切面板 | 切面板成功 → conversation 子树被卸载 → **对话框正住在那棵树里** → 刚创建就消失 |

用户看到的正是这个：面板切过去了（说明修复生效了），但没有对话框，所以也没有任何"开始直播"的动作。

**结构性错误是：我一直在同一个"谁负责弹窗、它住在哪棵树里"的问题上打补丁，
而没有一次把这个问题正面回答掉。** 正确的答案很简单：

> 负责弹窗的组件，不能住在任何会被导航卸载的子树里。

所以这一轮改的是结构，不是症状：

- 新增 `src/client/intent.js`：模块级的对话框意图（谁都能写，与挂载点无关）。
- 新增 `src/client/dialog-host.js`：**唯一**渲染对话框的宿主，注册在
  `shell.overlay`（官方定义："Frame-wide floating layer, above every column and
  outside their scroll containers"）——它常驻，切面板、切会话、切导航都不会卸载它。
- 会话页入口被压到最小职责：**只写意图，不切面板、不持状态**。
  "弹窗"和"导航"从此彻底解耦。

顺带修掉两个同一条链上的问题：

- **「开始直播」按钮一打开就是灰的**（要求先点过预览），配上不显眼的提示，
  用户读到的就是"按钮坏了"。现在打开对话框就自动加载预览，
  内容先渲染在按钮上方，按钮随之可用；万一仍不可用，理由会直接写在按钮旁边。
- 上面那个自动预览的第一版实现引入了 **16 号缺陷**（无限渲染循环），
  测试从 1 秒变成挂死 35 秒 —— 同样是渲染测试抓到的。

关于"下一轮该怎么做"：这三次失败有一个共同形状 ——
**我每次都验证了"我改的那一处"，但没有验证"用户完整走一遍"这条路径。**
所以这一轮补的关键测试是 `【回归】会话页入口被卸载（切主面板）之后，对话框依然在`：
它先把 `SessionEntry` 和 `DialogHost` 并排渲染，点击弹窗，**然后把 `SessionEntry` 整个卸载掉**，
再断言对话框仍在。它把那条教训固化成了断言，而不是又一句注释。

### 4.5 「后台在直播吗」——用数据回答

用户的追问是合理且重要的，所以这里给出可复现的检查方法，而不是一句"应该没有"。

直播间的生命周期完全在进程内，**创建它的唯一入口是 `live.open`**，
而 `live.open` 只由开播对话框的「开始直播」按钮调用；
Host 侧还会强制要求带 `previewed: true`。没有这个调用，就：

- 没有任何直播间对象；
- `ConsentGate` 不会产生任何授权（开播与授权是同一步）；
- 采集层因为查不到授权，会把事件**丢弃在归一化之前**（连深拷贝都不做）。

检查方法（本机实测结果）：

```sh
$ ls ~/.dsh/dsh-chat/
identity.json   peers.json          # 没有 audit.jsonl，没有 shares.json

$ cat ~/.dsh/dsh-chat/audit.jsonl
文件不存在 → 从未授权过任何会话外发

$ cat ~/.dsh/dsh-chat/shares.json
文件不存在 → 从未创建过任何分享

$ cat ~/.dsh/dsh-chat/peers.json
{ "relations": {}, "requests": {} }   # 也没有建立任何好友关系
```

`audit.jsonl` 只在授权/撤销/拒绝真正发生时才会被创建。它**不存在**，
就是"从来没有内容被批准外发"的直接证据 —— 不是推断，是文件系统的事实。

界面上也可以自查：**我的 → 直播管理**（应为空）、**我的 → 隐私与授权**（应为空）、
**节点 → 会话采集**（`因未授权跳过` 会持续增长，`已采集` 保持 0）。

### 4.6 渲染冒烟测试（无浏览器环境下能做到的最强验证）

`test/client-render.test.js` 用 react-test-renderer 把**真实的客户端组件**
（通过 esbuild 单独打一份测试用 ESM bundle，不是副本）渲染出来，并用一个
"缺方法就报错"的假 Host 通道喂进与真实 RPC 同形状的数据。

它覆盖：六个主视图、发现页的三个页签、分享对话框（含未预览禁止发布 →
预览后看到脱敏结果）、开播对话框、直播间的主播/观众两种角色、暂停提示、
会话页入口的两种状态、以及 **RPC 失败时是否显示错误而不是白屏**。

这个套件又抓到 2 个真实缺陷：

| # | 缺陷 | 表现 | 根因 |
|---|---|---|---|
| 9 | **JSX Fragment 未导入** | 好友页一渲染就抛 `Fragment is not defined`，整个 slot 变空白 | 用 `<>…</>` 的 7 个文件都没有把 `Fragment` 带进作用域。esbuild 把 `<>` 编译成 `Fragment(...)`，但那是个自由变量。**这类 bug 静态检查看不出来，只有真的渲染一次才会暴露** |
| 10 | **把 Error 对象当 React 子节点** | RPC 失败时不是显示错误，而是界面整个崩掉 | `ErrorLine` 直接渲染 `{error}`，React 抛「Objects are not valid as a React child」。**最讽刺的一点：出错处理路径本身会把界面弄崩** |
| 11 | **RPC 报文层次读错** | 界面上所有操作都报「未知方法: dsh-chat/rpc」 | 把信封的 `method`（= 端点名）当成了业务方法名；真正的业务调用在 `payload.method`。契约见 `@deepseek-ai/dsh-client-connection` 的 `createWebConnectionRpc` |
| 12 | 测试桩把两条路由互相覆盖 | 降级通道测试假失败 | 假 ctx 的 `webServer.register` 只记最后一个路由，而实际会注册 RPC 与 SSE 两条 |
| 13 | **`ctx.get()` 一次性快照** | 会话页的「分享会话 / 开启直播」点了没反应 | `const layout = ctx.get('layout')` 取的是 apply 那一刻的快照；服务没就绪就永远 undefined，`selectPanel()` 于是变成静默空操作 |
| 14 | **同一个 Fragment 缺陷复发** | `SessionEntry` 一渲染就抛 `Fragment is not defined` | 新增的 `<>…</>` 又忘了导入 `Fragment`（第 9 条是同一类）。已加结构性检查从机制上杜绝 |
| 15 | **对话框住在会被导航卸载的子树里** | 点「开启直播」跳到面板后，对话框凭空消失，看起来像"什么都没发生" | 对话框渲染在 `conversation.session.header.actions` 的组件里，而"切主面板"会卸载整个 conversation 子树 —— 组件和它刚创建的对话框一起没了 |
| 16 | **effect 依赖不稳定造成无限渲染循环** | 测试静默挂死 35 秒；真机上表现为界面卡住 | 自动加载预览的 `useEffect` 依赖里放了 `useAction()` 返回的对象，它每轮渲染都是新的 → effect 每轮重跑 → `setBusy` 触发下一轮渲染 |
| 17 | **重置 previewed 把自己锁死** | 取消勾选任一内容类型后，发布按钮永久灰着，理由还写着"正在加载预览…" | 勾选变化时把 `previewed` 置回 false，而自动加载的 effect 依赖没变、不会重跑 —— 用户被卡在一个假的加载态里 |

第 10 条尤其值得强调：它意味着"后端挂了"会表现为"整个面板白屏"，
而这恰恰是用户最需要看到原因的时刻。

它的边界也说清楚：**没有真实布局、没有主题、没有交互、没有浏览器**。
它证明的是"组件拿到真实形状的数据能渲染出预期文字且不抛错"，
不是"界面好看/正确"。

## 四点五、一次真实事故的完整记录（2026-10-11）

**现象**：重启 DSH 后界面显示「无法访问 dsh-chat 的 Host 半体」。
客户端半体是活的（`sidebar.panellist` 里有 `dsh-chat` 占位，`active: true`），
Host 路由却完全没注册（`GET /dsh-chat/events` → 404）。

**排查过程**（每一步都是实测，不是推断）：

| 检查 | 结果 |
|---|---|
| `Config.listConfigs` | 条目存在（`include:dsh-chat`，patch 已应用） |
| Host 半体在 DSH 运行时里 import | 正常（Node 24.18.1） |
| `lib/index.js` / `package.json` / 软链 / bundle 列表 | 全部正常 |
| 客户端 Slots | `dsh-chat` 占位存在且 active |
| 插件数据目录 | 重启后**没有任何写入** |
| 加入 `boot.json` 诊断后 | `phase = apply-called` —— **进入了但没走完** |
| 触发加载器重试（禁用 → 启用） | 拿到确切异常 ↓ |

```
dsh-chat: TypeError: 身份记录缺少加密密钥；应先用 migrateIdentityRecord 补齐
    at identityFromRecord (lib/index.js:1318)
```

**根因**：`identity.json` 是加入端到端加密**之前**写的，只有 Ed25519 签名密钥。
给 `identity.js` 写了 `migrateIdentityRecord`、也写了"插件会自动补上并落盘"的说明 ——
**但忘了把迁移接进加载路径**。于是老文件让 `identityFromRecord` 直接抛错，
`apply()` 中途失败，整个插件起不来。

**为什么 287 项测试没抓到**：它们**全部从空数据目录启动**，
没有任何一项覆盖"数据目录里已经有老格式文件"这个升级路径。

**修复**：
1. 加载路径接上迁移，并立即落盘（**签名身份一字不改**）；
2. 新增「升级场景」用例：造一份旧格式 `identity.json` 再启动插件；
3. 同一条用例顺带发现**第二个同类缺陷** —— `shares.json` 若不是数组，
   `for...of` 会抛 "not iterable"，同样让插件起不来。已改为显式判数组。

**事后确认**：迁移后插件正常加载，指纹仍是 `2fe33ea8-d8c4380f-9434d9ae-63472359`
（签名身份未变），独立进程握手验证通过。

**教训**（已写进代码注释）：
- 数据迁移必须**接进加载路径并有测试**，"写了迁移函数"不等于"迁移会发生"；
- **不要让一个字段的格式问题毁掉整个插件的加载** —— 坏数据应当降级 + 记账；
- 不要对未经验证的行为下结论。我此前对用户说"插件会自动补上并落盘"，那句是错的。
