# 打洞 · 中继选择 · 信誉与激励

中继让"连不上"变成了"能连上"，但代价是：流量经过第三方、消耗别人的带宽。
本文写清三件把它拉回来的事 —— **打洞**（省钱）、**选择**（别把流量交给坏节点）、
**信誉与激励**（谁贡献、谁消耗，以及不用代币怎么记）。

---

## 一、打洞（规划 §9.4）

### 1.1 原理

NAT 的本质是：**只有你先出站，别人才进得来**。打洞就是利用这一点：

```
① A、B 各自向中继问"你看到的我的公网端点是什么"     ← 等价于 STUN
② 双方经中继交换这两个端点（信令）
③ A、B 同时向对方的端点发起连接
   → A 的出站让 A 的 NAT 记住了 B，B 的出站让 B 的 NAT 记住了 A
④ 打通就直接用；没打通就退回中继
```

**打洞不改变可达性，它只省钱**：打通后用的是两台机器的直连带宽，不占中继带宽，
也不让第三方看到元数据。

### 1.2 NAT 类型决定成败（虚拟网络实测）

| 组合 | 结果 | 说明 |
|---|---|---|
| 全锥形 + 全锥形 | ✅ 打通 | 一条映射对所有人敞开 |
| 受限锥形 + 受限锥形 | ✅ 打通 | 双方都会先发一包，对方因此被"记"进 NAT |
| 全锥形 + 受限锥形 | ✅ 打通 | |
| **任一侧对称** | ❌ 失败 | 出站换端口，对方算出来的端口对不上 |
| 双方都是公网主机 | ✅ 直接可达 | 根本不需要打洞 |

对称 NAT 下**打洞必然失败**，所以实现里直接**跳过**，不浪费那几百毫秒：

```
对称 NAT：打洞失败（symmetric-nat-mismatch，被 gwA 挡住）→ 只能走中继
对照 · 全锥形：同样的流程打通（full-cone-open-mapping）
```

### 1.3 「不知道」不等于「可以打」

`inferNatType` 需要**至少两个观察点**才能区分锥形与对称（判据是"同一本地端口去不同目的地，
公网端口变不变"）。只有一个观察点时如实报 `unknown`。

这是很多打洞实现自欺欺人的地方：把 `unknown` 当成"可以打"，然后每次连接都白试一轮。
本实现的态度是 —— `unknown` 仍然值得一试（比放弃好），但**如实标注它是未知**，
而不是伪装成"已确认可行"。

> 回环地址是例外：看到的是 `127.0.0.1` 就说明没有 NAT，这**不需要第二个观察点**。

### 1.4 必须说清楚的限制：TCP 打洞比 UDP 脆弱得多

本项目的传输层是 **TCP + WebSocket**：

- **UDP 打洞**没有握手，双方各发一个包就形成两条映射，天然适配打洞；
- **TCP 打洞**需要**同时打开**（simultaneous open）——双方的 SYN 交叉发送，
  要求两边 NAT 都愿意转发"不是自己发起的那条连接的第一个包"，还要求操作系统支持。
  **很多 NAT 和系统不支持。**

本实现能做到的是**交换候选地址、挑一个能通的**（双方同时拨号，任意一条建立即成功）。
做不到的是把出站 socket 绑到监听端口上 —— 那才是 UDP 打洞真正依赖的东西。

所以态度是：

- 打洞**尽力而为**，成功就省下中继带宽；
- **中继永远是可靠兜底**，打洞失败不影响可用性；
- 对称 NAT 直接跳过，不浪费那几百毫秒。

真正稳妥的解法是把传输层换成 UDP（WebRTC / QUIC 那条路），那是传输层改造，
不在本次范围内。**这里不假装打洞在 TCP 上和在 UDP 上一样管用。**

### 1.5 三级决策

```
ensureReachable(peerKey)
  ├─ 已经直连            → direct（already-connected）
  ├─ 试打洞，通了        → direct（punched）
  └─ 否则                → relay（兜底）
```

界面上还能手动触发（`relay.punch`）。有节点**只能经中继到达**时，会**后台**试一次打洞 ——
刻意不做成同步等待：打洞要几秒，而中继本来就能用，让用户为了一个"可能更快"的路径干等，
是拿确定性换可能性。

## 二、多中继选择

引入多台中继之后，问题从"能不能连"变成"交给谁"。打分把四件事放在一起权衡：

| 因子 | 权重 | 为什么 |
|---|---|---|
| **用户手动指定** | +40 | 信任是用户给的，不该被算法盖过 |
| 已登记 | +20 / 未登记 −60 | 没登记就什么也做不了 |
| **目标亲和性** | +30 | 上次能通，这次大概率也能通 |
| **本地成功率** | ±30 | 实测比任何声明都可靠；用拉普拉斯平滑，样本少时向 0.5 收缩 |
| 连续失败 | −8/次（上限 −40） | 出问题了就先让开 |
| 负载饱和度 | −30×饱和度 | 别把大家都挤到同一台 |
| 被拉黑 | −1000 | 直接出局 |

**转发不再"发给所有中继"**。早先是无差别地发给每一台已登记中继 —— 那样虽然一定能送到，
但流量要乘以中继数量，还会把消息交给用户并不信任的节点。现在只发给打分最高的那台；
它回 `unreachable` 才换下一台。

`relay.unreachable` 还要**区分两种原因**，因为对信誉的含义完全相反：

- `not-registered` / 目标真的不在线 → 中继没做错什么
- `refused:plaintext-refused` → **中继违背了职责**（它承诺转发密文却没转），
  而且用户会以为消息发出去了 —— 这是静默失败，重罚并拉黑

## 三、信誉与激励（规划 §9.5）

规划 §9.5 明确反对过早引入代币。本模块照做：**本地信誉账本 + 贡献记账**，没有链上激励。

### 3.1 本地观察优先，他人证明只作参考

```
本地实测   权重最高 —— 自己看到的才算数
他人证明   只用来排序"我还没试过的那些"
```

**为什么刻意压低他人证明**：女巫攻击的成本只是"生成一堆密钥"，而伪造好评的收益是
"把所有流量引到一台坏中继上"。如果他人证明的权重能盖过实测，这个模块就成了攻击工具。

`AttestationBook` 还做了两件事：**同一评价者去重**（防刷）、**评价者数量上限**（防批量灌入），
并且样本 < 8 时标记为 `trustworthy: false` —— **3 条好评说明不了任何事**。

### 3.2 行为权重：不把别人的问题记在中继头上

| 观察 | 分值 | 说明 |
|---|---|---|
| 成功转发 | +1 | |
| 目标不可达 | −0.05 | **不计入连续失败** —— 目标不在线是网络现实，不是中继的错 |
| 登记被拒 | −0.5 | **不计入连续失败** —— 通常只是容量满了 |
| 无理由断开 | −2 | |
| **拒绝转发密文** | **−8，立即拉黑** | 拿了中继的角色却不干活，而且用户以为发出去了 |
| **转交伪造身份文档** | **−25，立即拉黑** | 试图做中间人 |

连续 5 次失败才拉黑；**一次成功即恢复**。

> 修正过一次的 bug：`UNREACHABLE` 原本会累加"连续失败"，于是 20 次"目标不在线"
> 就能让一台好中继被拉黑 —— 那是把别人的问题记在它头上。

### 3.3 激励：不使用代币的贡献账本

```
servedBytes    本机做中继转发出去的
consumedBytes  本机经中继消耗的
balance        净额（正数 = 净贡献者）
```

这只是**如实记账给用户看**，不假装能自动结算。规划 §9.5 反对过早引入代币，这条正好对应 ——
把"谁贡献、谁消耗"变得可见，已经能支撑"我该不该也开中继"这个判断。

### 3.4 信誉消除不了什么（必须如实说）

- **一台中继可以一直表现良好，然后在关键时刻作恶。** 信誉是历史，不是保证。
- **元数据仍然暴露**：中继能看到谁在和谁通信、多大、多频繁。
- **它可以拒绝服务**，规划 §12.5 已把它列为已知威胁。

缓解只能靠：用户手动指定自己信任的中继、多中继并用、以及打洞成功时根本不经过第三方。

## 四、配置

```yaml
relay:
  enabled: true
  serve: false
  servers: ['203.0.113.7:47800']
  punch:
    enabled: true          # 打洞；失败完全正常，中继兜底
    timeoutMs: 4000        # 太长会让用户干等
    dialTimeoutMs: 2500
  policy:
    maxPeers: 32
    maxEnvelopeBytes: 262144
    maxForwardBytesPerMinute: 8388608
    peerTtlMs: 90000
    requireSealedForPrivate: true
```

界面：**节点 → 中继（公网节点）**，包含打洞统计与 NAT 类型判定、中继信誉排序、
贡献账本。

## 五、测试覆盖（37 项）

| 组 | 项数 | 覆盖 |
|---|---|---|
| NAT 类型推断 | 6 | 单观察点必须报 unknown、端口一致→锥形、端口变化→对称、回环→open、对称直接跳过 |
| 虚拟网络打洞 | 6 | 全锥/受限可打通、任一侧对称必失败且标出"需中继"、公网主机直接可达、失败不是异常 |
| 打洞协调器 | 5 | STUN 探测、双方交换候选后打通并切直连、无中继时跳过、对方不在线时干净失败、三级决策 |
| 中继选择 | 7 | 手动指定优先、未登记降权、成功率排序、小样本不封神、负载降权、目标亲和性、拉黑出局 |
| 信誉 | 12 | 各类行为权重、拒绝密文立即拉黑、不可达不算中继的错、连续失败与恢复、手动拉黑、贡献账本、他人证明去重与上限、退避封顶 |

实测输出：

```
全锥形 + 全锥形 → 打通（full-cone-open-mapping）
受限锥形 + 受限锥形 → 打通（先发出的那一包把对方"记"进了 NAT）
全锥形 + 对称 → 打不通（symmetric-nat-mismatch）→ 必须走中继
中继观察到本机端点 127.0.0.1:55217；NAT 类型推断为 open（回环无 NAT）
打洞协调成功：A 用 2ms、B 用 2ms；关系已切换为直连
没有中继 → 打洞直接被跳过并说明原因，而不是干等到超时
对方不在线 → 打洞 4001ms 后失败（punch-timeout），中继连接不受影响
可达性决策：能打通的走直连（punched）；打不通的回落中继（punch-timeout）
贡献账本：转发出去 10000、消耗 2500、净额 7500
```

## 六、过程中修掉的真实缺陷

这轮打洞实现踩到的坑，都是"看起来在工作、其实没有"的类型：

| # | 缺陷 | 症状 |
|---|---|---|
| 1 | 中继客户端**吞掉**打洞控制消息（`default: break`） | 协调器永远收不到端点与候选，每次 `punch-timeout`，**日志里一个字都没有** |
| 2 | 只暴露 `remoteAddress`（纯 IP，**没有端口**） | 中继回答 STUN 探测时给出 `127.0.0.1`，解析不出端口 → 静默丢弃。丢在一个"看起来有值、其实缺一半"的字段上 |
| 3 | 候选只含观察端点，漏了本机监听地址 | 拨的其实是"连中继那条出站连接"的临时端口，上面没有监听任何东西 |
| 4 | 打洞信令被塞进 `RELAY_FORWARD` | 被中继的明文闸门判定为"明文私聊"直接拒转，信令一个字都出不去 |
| 5 | `RelayTransport` 没透传 `punch-*` 事件 | **协调器在跑，但外界一个事件都收不到** |
| 6 | 只认"我这条拨号"的结果 | 双方同时打洞时两条连接任意一条成功即算成功，只盯自己那条会让双方都判失败 |
| 7 | 收到 offer 且自己没有 pending 时直接 `return` | 单方面发起打洞（`ensureReachable`）永远超时 —— 打洞是双向协议，收到请求必须应答 |
| 8 | `emit('error')` 没有监听器会**抛异常** | 打洞时被去重关掉的那条重复连接触发 `ECONNRESET`，直接掀掉进程 |

第 1、2、5 条的共同教训：**"没有报错"和"工作正常"是两件事**。
三处都是静默丢弃，只在测试断言"确实收到了"时才暴露出来。

第 8 条已在 `NodeTransport` 基类修掉：构造时挂一个只记日志的兜底监听器，
调用方仍可再加自己的监听器。这是本项目**第二次**踩同一个坑（第一次在故障注入代理的定时器里）。
